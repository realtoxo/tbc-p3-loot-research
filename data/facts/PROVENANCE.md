# Facts

## Naming

One subject per file. Lowercase, hyphenated. `.csv` where the facts are tabular
and every row has the same shape, `.yaml` where they are structured or carry
prose. Three of these files answer "what exists": `drops.csv`, `items.csv` and
`item-effects.csv`. The rest answer "how does it work" or "who is here".

**Tiers are a column, never a filename.** There is no `t5-drops.csv`. Splitting
by tier would make the common question, which is how a Tier 6 piece compares
with what a player already wears, into a join across two files, and it would
double every time the project grew.

The `tier` column carries `T4`, `T5` or `T6` and appears on all three
generated tables. It is derived once, in `extract_drops.py`, from the zone map;
`items.csv` and `item-effects.csv` copy it across rather than re-deriving it,
so there is one place to change when a tier is added. Six Tier 6 items drop in
both Mount Hyjal and Black Temple, so an item can hold more than one zone. No
item in this scope crosses a tier boundary, but the column is pipe-separated in
the item tables in case one ever does.


Everything here is verifiable against a source: the game, the item database, or the guild lead.

`sim-profiles/token-arithmetic.yaml` holds only what is checkable about a token: which piece replaces which, the EP figures, the verbatim set bonus tooltips and the slot collisions. What those add up to for a spec is a reading, and every reading moved to [`data/judgments/token-verdicts.yaml`](../judgments/token-verdicts.yaml) on 9 August 2026.

Some of these files are machine-produced and some are hand-authored. That distinction does not decide where a file lives; **fact against judgment does**. A hand-written record of which buffs the raid runs is still a fact.

The nine generated files are rebuilt by `just regen` and must never be hand-edited. The 16 authored files each carry their own header stating scope, method and confidence, and each carries an `open_questions` block recording what is not settled. Those blocks are the honest edge of this data and are worth reading before citing a number.

`hit.yaml`, `crit.yaml`, `haste.yaml` and `attack-power.yaml` divide one subject four ways on purpose, so that each file name states exactly which mechanism a reader will find inside. Attack power is neither crit nor hit, so it takes its own file rather than a block inside `crit.yaml`.

`item-effects.csv` records the buff an item grants, its duration, and the stats
it confers. It does **not** record the trigger: proc chance, procs per minute,
or internal cooldown are not in the item database and live in the simulator
source. Knowing that Madness of the Betrayer grants 300 armor penetration for
ten seconds is not the same as knowing how often. For the T6 effect rows and
the trinkets the hit captures wear, the trigger data is collected in
`item-procs.yaml`.

It carries a `tier` column so that a Phase 3 trinket can be put beside the Tier
4 and Tier 5 trinkets it displaces without a join. There are 128 effect rows, of which 51 belong to trinkets. The tier
column is empty on 71 of them, because the widened item scope reaches items no
zone map assigns a tier to.

`items.csv` carries one row per item with every stat the item database
records, plus its tier, sockets, socket bonus, and weapon damage and speed. Stat indices
are transcribed from `proto/common.proto :: enum Stat`, never inferred.
Thirty items have no stat line. Seven are relics, an idol, a totem or a libram
in each tier. One is a weapon that carries damage and speed but no stats. The
other eight are trinkets whose whole value is an effect, so they carry a row in
`item-effects.csv` instead. Regenerate with `just regen`.

**Four populations share this table, and the `source` column tells them apart.**
957 rows: 489 `raid_drop`, 255 `tier_vendor`, 99 `drop`, 65 `crafted`, 25 `arena`, 12 `worn`, 12 `badge`. `raid_drop` is every item in `drops.csv` and
`tier_vendor` every tier set piece in `tokens.yaml`. The workbook routes
`drop`, `crafted`, `arena` and `badge` mark an item the EP Workbook ladder
names that neither of those reaches, and `worn` an item only a captured gear
set names, which is the relic slot entirely plus a few badge and arena pieces. Tier pieces are bought from a
vendor with a token, so they appear in no boss loot table and were absent here,
yet almost every priority on a Phase 3 drop is argued against the tier piece it
competes with. A named alternative that is not in the item table is one argued
about from memory, and it cannot be linked or given a tooltip in the compendium
either. The `tier` of a tier piece comes from the `tier` field of the set that
lists it, never from a zone; the two populations do not overlap on any id.

Requiring the two to agree is the cross-check that earns the widened scope.
`tokens.yaml` was hand-authored from the Wowhead 2.4.3 tooltip endpoint and
this database was captured separately, so the extractor asserts that all 255
ids resolve in the database and that the database spells each name exactly as
`tokens.yaml` claims. It exits non-zero if any one of them disagrees. No tier
piece has an item effect, so `item-effects.csv` is unchanged by this scope.

`class_allowlist` **was wrong for every class from Shaman onward and is now
correct.** The transform mapped the wowsims proto enum onto a field the database
fills with WoW's own ChrClasses ids. The two agree through Priest and diverge
after, so the error was invisible on five classes and labelled every Shaman set
`Druid`, every Druid set `11`, every Mage `Warlock` and every Warlock nothing.
Fixed by reading the enum the source actually uses, verified against four known
tier helms. The class that owns a SET is still best read from `tokens.yaml`,
which is hand-verified, but the column no longer disagrees with it.

Derived analysis lives in `data/derived/`, is regenerable, and is not committed.

### Source

The **WoWSims TBC item database**, `assets/database/db.json`, 8,254 items, from a checkout of `github.com/wowsims/tbc-new` fetched 2026-04-12. MIT licensed.

### How zones and NPCs were resolved

A drop record in `db.json` holds three fields, `difficulty`, `npcId` and `zoneId`. **No zone name and no NPC name appears anywhere in the file.** Both maps in `tools/extract_drops.py` are therefore external, and neither may be assumed from an id that looks right. Two bugs in this project's history came from exactly that habit: an `ItemType` enum was guessed and filed every belt as a wrist item, and a workbook tab was matched on its filename so the Protection Warrior ladder was read as the Protection Paladin.

The procedure, applied to every zone in the table and every NPC in it:

1. Collect every `npcId` that drops in the candidate zone.
2. Read each NPC from `https://nether.wowhead.com/tbc/tooltip/npc/<ID>`. That endpoint serves the TBC 2.4.3 data environment as JSON and returns the NPC's name together with its own `map.zone`.
3. Require the NPC's `map.zone` to equal the drop record's `zoneId`. Two fields of the same record, populated by different systems, agreeing is the check. Every NPC in all seven zones agreed.
4. Compare the resulting roster against the encounter list on `warcraft.wiki.gg`, fetched as wikitext with `?action=raw`.

Zones examined and **rejected**, resolved the same way: 3805 Zul'Aman and 4075 Sunwell Plateau and 4131 Magisters' Terrace, all later than this scope; 3847, 3848 and 3849, the three five-man wings of Tempest Keep; 3789 to 3792, the Auchindoun wings; 3713 to 3717, the Hellfire Citadel and Coilfang five-mans; 3562 Hellfire Ramparts; and 1583 through 3456, the classic-era instances. Coilfang and Tempest Keep each publish four zone ids and only one of each is the raid, which is the trap the procedure exists to catch.

Two endpoints matter here and the difference is not cosmetic. `nether.wowhead.com` answers automated clients; `www.wowhead.com` and `tbc.wowhead.com` are CloudFront-blocked and return **403**. `warcraft.wiki.gg` is reliable for rosters and names but has been caught serving post-TBC item values, so no number in this repository comes from it.

### Why not Wowhead

Wowhead's loot tabs are rendered client-side, so an HTTP fetch returns page chrome without the table, and CloudFront answers non-browser clients with **403**. The database carries the same drop data offline, and also carries each item's stat vector, which the scoring pipeline needs later anyway.

### Verification

Cross-checked against an independent browser-driven capture of Wowhead's loot tabs. Six Black Temple bosses were confirmed directly and every count matched. The three that capture could not resolve, namely Shade of Akama, Teron Gorefiend and Reliquary of Souls, fell out unambiguously because their counts are distinct at 14, 12 and 13, which also pinned down the Reliquary NPC id that the capture had failed to find.

Two independent sources agreeing across all nine bosses is stronger than either alone. Those expected counts are now asserted in the extractor; it exits non-zero if the database ever disagrees.

Tier 4 and Tier 5 rest on a different footing and the extractor labels the difference rather than hiding it. The **rosters** are cross-checked, by the NPC-side zone field and by the wiki encounter list, and it is the roster that could have been wrong. The **per-boss item counts** are a snapshot of this database, not a second source. They are asserted anyway, so that a change in the database or in the zone map becomes a crash rather than a quiet edit to the CSV, but they are weaker evidence than the Tier 6 block and should not be cited as confirmation.

The extractor also asserts the encounter count per raid, because a boss that disappeared from the NPC map would disappear from the count dictionary at the same time and so would never be missed by a count check alone. Karazhan asserts 11 encounters rather than the wiki's 12, for the reason in the traps below.

### Traps

**Do not filter by `db_phase`.** The field is wrong for at least the nine Ashtongue Talismans (32485 to 32493), which are labeled Phase 5 but are Black Temple rewards. Filtering by phase silently drops nine real Phase 3 trinkets. Filter by zone. This holds for the new zones too; the tier a row carries comes from its zone and never from `db_phase`.

**Tier tokens are not in this table, in any tier.** The database models the tier pieces, not the tokens. Tier 6 shows it at Mother Shahraz, 6 rather than 9, and at Azgalor, 6. The same subtraction runs through the earlier tiers: The Curator shows 6, High King Maulgar 6, Fathom-Lord Karathress 6, Leotheras the Blind 6 and Void Reaver 7. A boss whose count looks short is usually a boss that drops a token. Token data comes from the web and lives elsewhere.

**Karazhan has more boss NPCs than boss encounters.** Two of its encounters are randomised and the database keys loot to each variant's own NPC. The Opera Event is one encounter with three scripts, recorded here as The Crone, The Big Bad Wolf and Romulo. The Servant's Quarters rare is one encounter with three possible spawns, recorded as Hyakiss the Lurker, Shadikith the Glider and Rokad the Ravager. Fifteen names, eleven encounters. The wiki lists twelve; the twelfth is the Chess Event, whose reward comes from a chest rather than an NPC and so has no drop record at all.

**The `ItemType` enum is not intuitive.** It was transcribed from `proto/common.proto`, not guessed. An earlier hand-written version was off by one from Wrist onward and filed every belt as a wrist item. If you ever re-derive it, check a belt.
